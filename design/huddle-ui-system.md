# Huddle UI 与交互系统

## 0. 目的与边界

Huddle 是局域网派对的入口，而不是传统游戏平台。体验优先级为：

1. 用户明确知道下一步怎么加入或开始。
2. 网络、连接和房间状态始终可理解、可恢复。
3. 游戏成为视觉焦点，平台界面退到支持位置。

房主使用 Android 壳启动服务、邀请朋友和管理房间；房主 WebView 与客人浏览器使用同一套网页，完成大厅和游戏。原生壳不承载游戏界面或游戏规则。

## 1. 设计原则

- **少而准确**：每个面板、颜色和动效只服务于一个任务；不使用无意义的纹理、悬浮装饰或循环动画。
- **状态优先**：连接、席位、准备、轮次和错误必须以文字为主，颜色和图标为辅。
- **一致但不单调**：平台 Shell 保持稳定；游戏可在画布、`game-accent` 和局部插图中表达个性。
- **直接可逆**：常用操作单击完成；退出席位、结束房间等有影响的操作必须说明后果并允许取消。
- **可达性即默认**：触控、键盘、系统字体放大、深浅主题和弱网恢复均属于主流程。

## 2. 信息架构

### Host App

| 页面/层级 | 核心任务 | 必须可见的状态与操作 |
| --- | --- | --- |
| 首页 | 选游戏、创建房间 | 游戏可用性、游戏人数、主操作“开始房间” |
| 开房准备 | 等待本机服务与网络 | 当前进度、失败原因、重试/返回 |
| 房间壳 | 保持前台、进入同一网页客户端 | 服务状态、邀请、结束房间 |
| 邀请面板 | 让朋友加入 | 二维码、可复制链接、同一网络提示、连接人数 |
| 设置 | 主题 | 主题跟随系统 |

首页只出现一个主要操作。房间运行时，“邀请”固定在可触及区域；“结束房间”放入溢出菜单或二次确认，不与邀请并列。

### 房间网页 Shell

网页不以五子棋结构作为固定页面。所有游戏均使用下列三区：

1. **状态栏**：房间名称/游戏名、连接状态、必要的辅助操作。
2. **房间区**：备战席、观战席、准备状态与开始条件；进房自动入备战席，超出人数进观战席。游戏可替换席位呈现方式，但不可隐藏身份和状态。
3. **游戏区**：大厅说明、游戏画布或结算结果。游戏插件只填充这一层和其专属信息。

## 3. 关键旅程与状态

| 阶段 | 用户目标 | 界面反馈 | 主操作 |
| --- | --- | --- | --- |
| 选游戏 | 决定玩什么 | 可玩/即将推出、人数和时长 | 开始房间 |
| 启动服务 | 等待房间可用 | 进度文案；超过合理等待时间显示原因 | 重试、返回 |
| 邀请加入 | 让朋友正确进入 | 二维码、链接、同一 Wi-Fi/热点提示 | 复制链接、关闭 |
| 连接中 | 知道是否进入成功 | “正在连接房间”，不展示可误触的游戏操作 | 自动重连 |
| 大厅 | 自动入备战席并准备 | 备战席 / 观战席、人数、准备条件、主持人身份 | 观战 / 准备、入席 |
| 等待开始 | 明白谁在等待谁 | "等待 N 人准备"或"等待房主开始" | 准备/开始 |
| 对局 | 专注当前游戏 | 轮次、当前行动者、游戏规则内的必要状态 | 游戏操作 |
| 断线恢复 | 不丢失方向感 | 常驻但不遮挡的连接横幅；说明正在恢复 | 重试、离开房间 |
| 结算 | 理解结果并继续聚会 | 胜负/结果、简短回顾 | 再来一局、返回大厅 |

### 错误分级

- **就地校验**：备战席已满、未准备等可立即修正的操作，显示在触发控件附近。
- **可恢复横幅**：正在重连、服务暂不可达，说明当前保留的状态和重试进度。
- **阻断页/对话框**：无法创建房间、链接失效、房主结束房间。提供明确的唯一下一步。
- Toast 只用于“已复制”“已准备”等完成确认，不承载错误、离线或房间结束等重要信息。

## 4. 视觉基础

### 色彩 token

实现使用语义名而不是跨端复制十六进制。当前 Android `colors.xml`、`values-night/colors.xml` 与网页 `style.css` 是迁移起点；后续分别映射同一语义 token。

| 语义 token | 浅色建议 | 深色建议 | 用途 |
| --- | --- | --- | --- |
| `color-bg` | #F4F1EA | #0F1419 | 页面背景 |
| `color-surface` | #FFFFFF | #1A222C | 卡片、对话框 |
| `color-surface-muted` | #EBE6DB | #232B36 | 次级容器、禁用底色 |
| `color-text` | #1A2330 | #F2F5F8 | 主文字和图标 |
| `color-text-muted` | #5C6B7A | #9AA7B5 | 辅助文案 |
| `color-border` | #1A23301F | #FFFFFF1A | 边界与分隔 |
| `color-action` | #0F8F6C | #3DDC97 | 主操作、成功、在线 |
| `color-danger` | #C4473A | #E85D5D | 破坏性操作与错误 |
| `color-warning` | #B08900 | #E0B44E | 警告、即将推出 |
| `game-accent` | 游戏定义 | 游戏定义 | 仅游戏画布与专属信息 |

`color-action` 不用于所有强调。一个屏幕中最多一个主操作；不使用纯色大面积背景来制造视觉重量。

### 排版、间距和形状

| Token | 值 | 用途 |
| --- | --- | --- |
| `space-1/2/3/4/6/8` | 4/8/12/16/24/32 px | 仅使用此间距阶梯 |
| `radius-sm/md/lg` | 8/12/16 px | 控件、列表项、卡片 |
| `type-title` | 28/34, 700 | 页面标题 |
| `type-section` | 20/26, 650 | 区块标题 |
| `type-body` | 16/24, 400 | 默认正文与主操作 |
| `type-meta` | 14/20, 400 | 辅助信息 |

优先使用系统中文字体栈。正文不得小于 14px；重要状态和主操作默认 16px。

## 5. 组件契约

| 组件 | 规则 |
| --- | --- |
| 主按钮 | 一个区域最多一个；高对比填充；最小 44×44px；加载时保留原文案并禁用重复提交。 |
| 次按钮 | 描边或低强调表面；不得与主按钮争夺层级。 |
| 图标按钮 | 必有无障碍名称；不可仅依赖颜色或隐晦图标表达危险操作。 |
| 卡片/面板 | 承载一组相关任务；优先边框与表面层级，避免多层阴影。 |
| 席位 | 同时显示身份、空闲 / 已占、准备与轮次；备战席满员时观战席入席按钮禁用并提示。 |
| 状态标签 | 文字优先，颜色与图标辅助；“房主”“已准备”“重连中”语义不可混用。 |
| 对话框 | 仅用于需要立即决策或打断当前任务的内容；主操作放右/下，取消操作可见。 |
| 结果层 | 给出结果、下一步和可关闭路径；不得自动跳走。 |

所有互动元素须具备默认、按下、禁用、加载、成功或错误状态；键盘可获得焦点时提供清晰焦点环。

## 6. 响应式与人体工学

- 使用 `100dvh`、安全区 inset 与流式宽度；不因固定高度遮挡主要操作。
- **窄屏（<600px）**：单列，主要操作位于拇指易达的下半区；页面内边距 16px，触控目标至少 44px。
- **中屏（600–1023px）**：房间区可与游戏区并列，主要画布获得更多空间；邀请和关键状态不随宽度漂移到不可见位置。
- **大屏（>=1024px）**：最大内容宽度 960–1200px；房间信息作为辅助栏，游戏区优先，不保留 480px 窄栏。
- 不设置 `user-scalable=no`；不得阻止系统缩放。画布游戏可提供自己的缩放、复位和双指手势，但页面文字仍服从系统缩放。
- 横向滚动只用于次要的观战者列表，需给出滚动提示；主要操作和席位不可依赖横向滚动。

## 7. 动效与反馈

- 按压反馈 100–150ms；状态切换 160–240ms；结果层入场不超过 280ms。
- 动效只表达位置、层级或操作结果。禁止自动播放的装饰动画与无限呼吸效果；连接加载可用短暂进度指示。
- 支持 `prefers-reduced-motion: reduce`：移除位移、缩放和循环动效，保留即时状态变化。
- 游戏插件可使用有限的规则内反馈（例如落子），但不能延迟输入确认或覆盖连接状态。

## 8. 可访问性验收

- 正文与背景对比度至少 4.5:1；大文字至少 3:1；状态不能只靠颜色。
- 所有操作有可见文字或可访问名称；图标不单独承担语义。
- DOM/焦点顺序与视觉顺序一致；弹层打开时聚焦首个可操作元素，关闭后回到触发点。
- 点击、拖拽和画布操作提供不要求精确手势的替代方式。
- 网络变化、胜负和房间结束应可被辅助技术读出，且不反复播报。

## 9. 当前代码映射与采用顺序

| 目标 | 当前落点 | 后续工作 |
| --- | --- | --- |
| 网页 token | `android-host/app/src/main/assets/www/style.css` | 将现有 `--ink`、`--paper`、`--accent` 等迁移为语义双主题 token。 |
| Android token | `res/values/colors.xml`、`res/values-night/colors.xml`、`themes.xml` | 保持 token 名称与网页语义一致，不直接复制 CSS 值。 |
| 共享网页 Shell | `assets/www/index.html`、`app.js` | 抽出状态栏、房间区和游戏区插槽，删除五子棋结构假设。 |
| 游戏 UI | `assets/www/games/<game-id>/` | 游戏只提供画布、专属状态和 `game-accent`。 |
| 服务端游戏契约 | `runtime/GamePlugin.kt`、`GameCatalog.kt` | 游戏状态须能表达上述大厅、对局、结算和恢复状态。 |

建议实施顺序：先建立双主题 token 和基础组件，再重构网页 Shell，随后以五子棋迁移验证，最后用下一款游戏验证插件边界。

## 10. 新游戏设计检查清单

- 是否能在不认识游戏规则时完成扫码、自动入备战席、准备和退出？
- 大厅是否只使用共享 Shell，而非改写平台状态与操作语义？
- 是否覆盖空位、人数不足、等待、行动中、断线、结算和重开？
- 是否在浅/深色、小/中/大屏、系统字体放大和减少动效下保持可用？
- 是否所有关键状态都有文字、图标或结构提示，而不仅是颜色？
- 是否没有用装饰、动画或游戏主题色抢占主操作和错误反馈？
